# 設計メモ(技術の想定)

機能仕様書(`機能仕様書.md`)の機能を、どの技術で実現するかの想定を残すメモです。実装を進めながら、決まったことを更新します。「確認済み」は、実際に動かした、または一次情報で確認した内容で、「未確認」は、まだ確かめていない内容です。

## 1. データ

- 前提: アプリを使うのは、作者 1 人だけ。認証(Cognito のログイン)は、認証をつけたかったために入れていて、複数ユーザーでの利用(別ユーザーの空の表示など)は、確認しない。ユーザーごとにデータを持つ作りは、そのまま残す。

- Quests の 1 テーブルだけで始める(履歴の Activity テーブルは、後回し)。
- クエストは、ユーザーごとに持つ。キーは、ユーザー ID(Cognito の `sub`)。
- テーブルは、CDK(`webapp/amplify/backend.ts`)で作る。Amplify Data は使わない。
  - 理由: エージェントと Astro のサーバーに、権限を明示して付けるため。
- 状態(未着手/閲覧済み/クリア済み)と復習候補は、Quests のクエストに持たせて保存する。問題への回答イベントなどの履歴は、週間レポート用の Activity テーブルで別に持つ。

## 2. データの読み書きの経路

```
画面 ──→ Astro /api/quests(JWT を検証)──→ DynamoDB(Quests)   ※表示。エージェントを通さない
エージェント(AgentCore)────────────────→ DynamoDB(Quests)   ※登録。boto3 で直接
```

- 表示を、エージェントを通さず API にする理由: 初回表示で、エージェント(LLM)を経由すると、応答が遅くなるため。
- エージェントは、Astro の API を呼ばない。ツール(Python の関数)が、`boto3` で、実行ロール(IAM)を使って直接アクセスする。
  - 確認済み: Strands の `@tool(context=True)` で、`ToolContext` を受け取れる(`agent/.venv` の `strands/types/tools.py`)。
  - 確認済み: `boto3` は、`agent/.venv` に入っている(1.43.102)。ただし、`pyproject.toml` には書かれていない。使うときに明示して足す。
- 権限:
  - エージェントの実行ロール: `agentRuntime.addToRolePolicy` で、テーブルへの読み書きを付ける。
  - Astro の SSR の Lambda: `webapp/amplify/hosting.ts` で、`dynamodb:Query` などを付ける(`InvokeAgentRuntime` を付ける処理と同じ形)。
- テーブル名の渡し方: `backend.addOutput({ custom: { questTableName } })` で、`amplify_outputs.json` に出す案。エージェントへは、環境変数(AgentCore の Runtime の `environmentVariables` が使えるかは、未確認)。

## 3. ユーザー ID のエージェントへの渡し方

- Astro のサーバーが、検証済みの JWT から `sub` を取り、AgentCore へのリクエストに入れる(画面から偽装できない)。
- `InvokeAgentRuntime` に、`X-Amzn-Bedrock-AgentCore-Runtime-User-Id` ヘッダーがある(AWS のドキュメントで確認。使うには、`InvokeAgentRuntimeForUser` の権限も要る)。
- エージェント側は、`ag-ui-strands` の `invocation_state_provider`(リクエストから、リクエスト単位の値を作る関数)で受け取り、ツールが `tool_context.invocation_state` で読む(型定義とソースで確認)。
- 確認済み: 実際には、ヘッダーではなく、リクエストの本文(AG-UI の `forwardedProps.userId`)に入れる方法で、動いた(手順書の第 12 章)。`create_strands_app` は `invocation_state_provider` を受け取る。署名つきの `fetch` で、本文を書き換えられる。
- 未確認: AgentCore が `X-Amzn-Bedrock-AgentCore-Runtime-User-Id` ヘッダーを、エージェントに渡すか(使っていない)。

## 4. 毎朝の自動更新(機能仕様書の F-10)

```
EventBridge Scheduler(毎日 6 時、日本時間)
  → Lambda(webapp/amplify/jobs/daily-quests/handler.py)
      ├ Cognito のユーザーを一覧(ListUsers)
      └ ユーザーごとに、AgentCore Runtime を呼び出す(SigV4 で署名した HTTPS。Web アプリのサーバーと同じ方法)
            → エージェントが、fetch_news(RSS の取得)→ list_saved_quests(重複の確認)→ save_quests(DynamoDB へ保存)
```

- Lambda(Python 3.13、タイムアウト 15 分)は、`backend.ts` の agent スタックに作る。権限は、AgentCore の呼び出し(`agentRuntime.grantInvokeRuntime`)と、Cognito の `ListUsers` だけ。
- Scheduler は、`cron(0 6 * * ? *)`、タイムゾーンは `Asia/Tokyo`。失敗しても再実行しない(`retryAttempts: 0`。モデルの呼び出しを、繰り返さないため)。
- Lambda が、AgentCore を、直接ではなく、間に挟む理由: ユーザーごとの繰り返し、AG-UI の入力の組み立て、SigV4 の署名、応答(SSE)を最後まで読んで、実行の完了を待つこと、が要る。Scheduler の汎用ターゲットで、`InvokeAgentRuntime` を直接呼べるかは、未確認(本文がバイナリで、ストリーミングの応答のため、向かないと考えている)。
- ユーザー ID は、リクエストの本文(`forwardedProps.userId`)に入れる(手順書の第 12 章と同じ)。定期実行であることは、`forwardedProps.batch` で伝え、記憶(AgentCore Memory)に、この会話を残さない(`PersistenceMode.NONE`)。読み出しは、行うので、関心に合うニュースを優先できる。
- 確認済み(ローカルから、Lambda のコードを実行): デプロイ済みのエージェントを、署名つきで呼び出し、ニュースの取得とクエストの保存が、27 秒で動いた。未確認: Lambda と Scheduler として、AWS にデプロイして動くこと。
- 決めたこと(機能仕様書の F-10): 直近 2 日、最大 5 件、失敗しても通知しない。

## 5. Generative UI(機能仕様書の 9 章)

方式の候補(CopilotKit のドキュメントの `generative-ui/` 配下 13 ページを確認。動作は未確認):

| UI | 場所 | 方式の候補 |
|---|---|---|
| 条件確認 | チャット | Interactive(承認フロー。`useHumanInTheLoop` か `useInterrupt`) |
| 理解度チェック | チャット | Interactive(回答を、エージェントに返す。`useHumanInTheLoop`。実装済み) |
| 次の操作候補 | チャット | Interactive |
| 週間レポート | チャット | Tool Call Rendering(集計はツール。描画は自作のカードとグラフ) |
| クエスト検索結果 | メイン領域 | API から取得して描画。チャットからの条件の変更は、フロントのツール(`useFrontendTool`。実装済み) |
| クエスト詳細(要約、参照元) | メイン領域 | API から取得して描画 |
| 比較表示、影響表示 | メイン領域 | JSON Render か A2UI(要検証。A2UI は、チャット内に描く前提のため、メイン領域に出せるかは未確認) |

- 実装済み(手順書の第 8 章): 理解度チェック(`useHumanInTheLoop` で `show_quiz` を登録)。表示、初回の回答をエージェントに返す(ツールの結果として、選んだ選択肢と正誤)、不正解のあとの再回答(画面の中だけ。初回の結果を残す)を、aimock のイベントで確認した。リクエストの `tools` に、`show_quiz` の名前、説明、引数のスキーマが入ることも確認した。問題への回答履歴の保存は、週間レポートと同じ段階で行う。
- 実装済み(手順書の第 9 章): チャットからメイン領域の更新。フロントのツール(`useFrontendTool`)の `update_quest_filter` が、クエストボードの検索条件(サービス、重要度、想定学習時間、期間、状態)を変える。変更前後の条件と件数を、チャットのカードに出し、ツールの結果としてエージェントにも返す。aimock のイベントで、サービスと想定学習時間の指定、0 件のときの案内、詳細を開いたままの更新、詳細を閉じたあとの条件の維持を確認した。未確認: 期間と重要度の指定、本物のエージェントが、自然言語から適切な引数で呼び出すこと。関心領域は、クエストのデータに項目がなく、未対応。
- 実装済み(手順書の第 10 章): クリアと回答後の操作。回答後に、「クエストをクリアする」「詳細へ戻る」「追加で質問する」を、問題のカードの中に出す。クリアは、回答済みでできる(機能仕様書 F-06)。不正解のままクリアすると、「復習」の印(復習候補)を付ける。クリア済みなら、「クリア済みです」を出す。チャット内の部品から画面を操作する窓口は、React の Context(`QuestActions`)。`show_quiz` に `questId` を足した。認証ありの環境では、閲覧済み・クリア済み・復習候補を `/api/quests` の `PATCH` で Quests テーブルへ保存する。問題への回答履歴は保存しない。F-09 の復習候補(初回不正解)と、F-06 の復習候補(不正解のままクリア)は、条件が違い、履歴を作るときにそろえる。
- AWS の `dev` 環境での確認(手順書の第 11 章): `agent/` を変更しない、汎用のアシスタントのままで、本物のエージェントが、`update_quest_filter`(自然言語の絞り込み)と `show_quiz`(問題の生成と、回答の受け取り)を呼び出した。確認済み。問題: エージェントがクエストの ID を知らず、`show_quiz` の `questId` が実際の ID と一致しないため、「クエストをクリアする」が効かなかった。対応の案: `useAgentContext` で、クエストの一覧と、開いているクエストを、エージェントに渡す(未実施)。
- 実装済み(手順書の第 12 章): エージェントの実装。ツールは `fetch_news`(What's New の RSS の取得)と `save_quests`(`boto3` で DynamoDB に保存。同じクエストは上書きしない)。画面の状況(クエスト一覧、開いているクエスト、検索条件)は `useAgentContext` で渡し、保存後は、フロントのツール `reload_quests` で、ボードを更新する。ユーザー ID は、サーバー(検証済みの JWT)が `forwardedProps.userId` に入れ、エージェントは `create_strands_app` の `invocation_state_provider` で受け取る(ローカルと AWS で確認済み。前は未確認だった点)。AgentCore の中から、RSS の取得と、DynamoDB への書き込みができることも確認済み。未確認: 別ユーザーの空の表示、件数が増えたときの扱い、重要度の基準。
- 実装済み(手順書の第 13 章): クエスト詳細の更新(F-03、F-04)。フロントのツール(`useFrontendTool`)の `update_quest_detail` が、詳細レイヤーに、比較表(`comparison`)、影響(`impact`)、文章(`text`)の表示を、追加・更新する(同じ `id` は置き換え)。見た目は固定で、エージェントは、種類と中身だけを決める。詳細を開いているクエストだけが対象(ほかは、エラーを返す)。追加済みの表示は、`useAgentContext` で渡す。保存はしない。aimock のイベントで、追加、更新、影響と文章の追加、開いていないクエストへのエラー、閉じて開き直しても残ることを確認した(a11y ツリーでの確認。スクリーンショットは、タイムアウトして、取れなかった)。未確認: 本物のエージェントが、適切な引数で呼ぶこと、見た目、スマートフォンの幅、ダークモード。方式は、エージェントが UI を組み立てる方式(A2UI、JSON Render)ではないため、「メイン領域の GenerativeUI」としては、固定部品の選択と、引数の生成に当たる。A2UI などで、メイン領域に出せるかは、引き続き未確認。
- aimock の制限: 固定のイベントの `toolCallId` は毎回同じなので、同じ会話で同じメッセージを 2 回送ると、2 回目は何も起きない(確認済み。再読み込みで、新しい会話にすると動く)。
- aimock で `events` を書くときは、`RUN_STARTED` と `RUN_FINISHED` も自分で書く(書かないと、「First event must be 'RUN_STARTED'」になる。確認済み)。
- チャットから検索条件を変えたときの、メイン領域の更新: エージェントが、検索条件かクエストの ID を、状態(`useAgent`)かフロントのツール(`useFrontendTool`)で渡し、フロントが API で取得し直す案(未確認)。
- 確認済み: `ag-ui-strands` に、フロントのツールの中断(`frontend_tool_interrupt.py`)、状態の共有(`config.py` の `predict_state` など)、A2UI のツール(`a2ui_tool.py`)がある。ただし、動作は未確認。
- 使わない方式: Open Generative UI、MCP Apps(制御が弱く、ブランドやアクセシビリティを保証しにくい)。

## 6. モック

- aimock の AG-UI のモックは、ツール呼び出し、状態、アクティビティなどのイベントを返せる(`@copilotkit/aimock` 1.43.0 の型定義で確認)。`webapp/mock/aimock.json` の `fixtures[].events` に、イベントの列を書く。
- 録画: `--agui-record` と `--agui-upstream <url>` で、本物のエージェントのイベントを、フィクスチャとして保存できる(コマンドラインのオプションで確認。動作は未確認)。設定ファイルでは、録画を有効にできない。
- `webapp/` の `npm run dev:mock`(認証なし)では、`/api/quests` は、DynamoDB を使わず、サンプルのクエストを返す。閲覧済み・クリア済み・復習候補は開発サーバー内のメモリに保持し、同じサーバーでの再読み込みを確認できる。DynamoDB のモックは、当面、これで足りる。
- DynamoDB Local(`amazon/dynamodb-local`)は、エージェントの保存ツールを作る段階 3 の直前に、必要になったら足す。接続先は、環境変数 `AWS_ENDPOINT_URL_DYNAMODB` で切り替える案。Python の `boto3` が対応していることは確認済み。JS の SDK は、未確認。テーブルの作成スクリプトが要る。

## 7. 週間レポート(草案。優先度は低い)

機能仕様書の F-08(週間レポートの自動作成の草案)に対する、技術の想定です。すべて、決まっていません。

```
EventBridge Scheduler(毎週日曜)→ Lambda → 履歴を集計(決まった規則)→ エージェントが所見を付ける → S3 に JSON を保存
ユーザーが「週間レポート」を依頼 → Astro の API(例: /api/reports/latest)が、自分のレポートを S3 から読む → チャットのカードに表示
```

- 数値は、履歴(Activity。F-07)を、決まった規則で集計して出す。エージェント(LLM)には、数値を計算させず、短い所見だけを書かせる想定(機能仕様書 IR-04 の、指標の一意な定義のため)。
- 保存先は、S3 に、ユーザーごと、週ごとの JSON(例: `reports/<ユーザー ID>/<週>.json`)。表示に必要な構造を、そのまま持つ。
- 読み出しは、クエストの API と同じく、Astro の API が、検証済みの JWT のユーザー ID で、自分のレポートだけを返す。
- 前提: 学習履歴(F-07。Activity テーブル)が要る。いまは、後回しにしている。
- 画面(チャット内のカードと棒グラフ)は、JSON の形が決まれば、モックのデータで、先に作れる。Tool Call Rendering(`useRenderTool`)の想定。
- 未確認: Scheduler から Lambda を呼び、エージェントを呼ぶ流れ(F-10 の毎朝の自動更新と共通)、S3 からの読み出し、ユーザーの一覧の取り方。

レポートの JSON の形(たたき台):

```json
{
  "userId": "…",
  "period": { "start": "2026-09-21", "end": "2026-09-27" },
  "generatedAt": "2026-09-28T06:00:00+09:00",
  "metrics": { "viewedCount": 8, "clearedCount": 5, "answeredCount": 6, "firstCorrectRate": 0.67 },
  "daily": [ { "date": "2026-09-21", "viewed": 2, "cleared": 1 } ],
  "breakdown": [ { "label": "AgentCore", "count": 4 } ],
  "comment": "…",
  "reviewQuestIds": ["…"]
}
```

回答数が 0 のときは、`firstCorrectRate` を出さない(機能仕様書 F-08)。
